Fewer comparisons, by construction.

Plain insertion sort compares each new element against everything before it. This algorithm pairs numbers up first, sorts only the "winners," then slots the "losers" back in — one at a time, in an order chosen so each search only ever spans as much of the list as it could possibly need. Why pair-and-recurse in the first place?

Splitting each pair into a winner and a loser and recursively sorting only the winners means that by the time any loser needs to be inserted, most of the chain is already correctly ordered relative to that loser's own partner. The insertion is still a search — but it's a search into a list that was never touched by that element before, so nothing is wasted re-comparing things you already know.

Why the Jacobsthal order, and not just 1, 2, 3…

Inserting losers in plain order (loser 1, then 2, then 3…) works, but it lets the search windows grow one element at a time in the worst case. Jacobsthal numbers (0, 1, 1, 3, 5, 11, 21…) group insertions so each new element is inserted while the chain is still as short as binary search can make useful — and crucially, within each group, insertions happen from the largest index down to the smallest, so the search bound (upperBound) for each one is as large as possible without ever needing to search past where its own partner sits.

Why insertGeneric only searches part of the chain

upperBound isn't arbitrary — it's the position of the loser's own paired winner inside the current chain. Since a loser is always smaller than its winner, and the winner's position is already known, there is provably no reason to search anything past it. That's the actual comparison-count saving; the Jacobsthal ordering just decides which loser gets to exploit the largest such window first.

About that first insertion (losers[0]): in this run, losers[0]'s partner (winners[0]) always happened to land at position 0 of the freshly-sorted chain, so every "insert first loser" step below needed zero comparisons. That's not a general guarantee — it depends entirely on where winners[0]'s value ends up after the recursive sort. Feed the algorithm different numbers and that first insertion can easily need a real binary search too. Worth keeping in mind if you're chasing an edge case around losers[0] specifically.
